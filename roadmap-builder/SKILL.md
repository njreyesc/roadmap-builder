# Roadmap Builder

**Быстрый старт по входным данным — `references/input-guide.md`.** Прочитай его
первым: там простыми словами, что дать на вход и как `capacity` влияет на сроки.

Строит roadmap из одного из двух видов входа:

- **Режим A — Excel-план работ** (спринты в колонках, люди/команды в строках, задачи в ячейках) — разбор и нормализация, см. «Как разбирать исходный план».
- **Режим B — список фич с оценками** (фичи уже согласованы и приоритизированы; по каждой — оценки фаз аналитика/разработка/тестирование) — декомпозицию по неделям делает детерминированный планировщик, см. «Режим B» ниже.

**Дефолт Режима B — максимальная параллельность фич.** Строй roadmap так,
чтобы все фичи шли параллельно и независимо, и **не задавай уточняющих
вопросов** — просто собери roadmap на дефолтах (см. «Режим B» ниже). Это
основной, ожидаемый по умолчанию режим. Эталонные примеры вывода:
`features_parallel.json` → `roadmap_parallel.xlsx` / `roadmap_parallel.pptx`.

Единственный рычаг сроков — поле `capacity` (пропускная способность команды),
и по умолчанию его **нет**:

- **Без `capacity` (дефолт)** — ресурсы не ограничены: у каждой фичи как будто свои выделенные люди, фичи стартуют одновременно и идут независимо. Пример: `features_parallel.json`.
- **С `capacity` (только по явной просьбе)** — общий пул: фичи набиваются в бак пропускной способности, что не влезло — разливается на следующие спринты. Чд-оценка без `people` занимает весь пул фазы, поэтому такие фичи идут в фазе по очереди (пайплайн по фазам). Включай, **только если пользователь сам сказал**, что команда одна и делит общий ресурс. Пример: `features.json`.

Подробно, с минимальными JSON-примерами — в `references/input-guide.md`.

Выход в обоих режимах одинаковый — roadmap двух видов:

1. **roadmap.xlsx** — таймлайн-сетка: месяцы → недели в шапке, дорожки (свимлейны) по фичам, вехи-ромбы, полосы работ с подписями («6 спринтов, 60 чд»), выноски-комментарии, отметка «сегодня».
2. **roadmap.pptx** — те же данные слайдами в стиле управленческой презентации: сетка недель, оранжевые/жёлтые полосы, зелёные (done) и белые с красным контуром (план) ромбы, голубые выноски, зелёная вертикальная линия «сегодня».

## Архитектура: parse/plan → JSON → render

Никогда не рисуй roadmap «вручную» напрямую из исходника. Всегда через `roadmap.json`:

1. **Получение `roadmap.json`** — зависит от режима:
   - **Режим A (Excel-план):** прочитай исходный .xlsx через openpyxl (включая заливки ячеек — цвет несёт смысл), пойми структуру, извлеки задачи и нормализуй в `roadmap.json` по схеме `references/data-schema.md`. Покажи пользователю краткую сводку того, что распознал (сколько дорожек, задач, вех), прежде чем рендерить.
   - **Режим B (список фич с оценками):** собери `features.json` по схеме `references/features-schema.md` (фичи, оценки фаз в человеко-днях по умолчанию — или в неделях/спринтах, опционально исполнители, зависимости `after`, вехи) и прогони планировщик:
     ```bash
     python scripts/plan_features.py features.json roadmap.json
     ```
     Планировщик раскладывает фазы каждой фичи (аналитика → разработка → тестирование) по неделям и печатает сводку по фичам — покажи её пользователю перед рендерингом. Фазы идут с нахлёстом: по умолчанию `overlap: 0.5` — следующая фаза стартует, когда предыдущая наполовину готова. Поле `overlap` в features.json меняет это — доля предыдущей фазы или недели (`1`), глобально или на фичу; строгая последовательность — `"overlap": 0`; см. `references/features-schema.md`. Ручные точечные сдвиги — правь уже сгенерированный `roadmap.json`.
2. **Рендеринг скриптами:**
   ```bash
   python scripts/build_xlsx.py roadmap.json roadmap.xlsx
   python scripts/build_pptx.py roadmap.json roadmap.pptx
   ```
   Скрипты детерминированные — не переписывай их под конкретный файл. Если чего-то не хватает, расширяй JSON-схему и скрипты, сохраняя обратную совместимость.

### Источник: текстовый список фич

Самый лёгкий вход — одна строка на фичу: название и рядом текстом оценки трёх фаз (из Jira скопирован список эпиков, оценки дописаны текстом). Конвертер:
```bash
python scripts/text_to_features.py features.txt features.json \
    [--capacity analytics:10,dev:15,testing:10] [--start 2026-07-20] [--title "..."] [--today ...] [--sprint-weeks 2]
```
`--start` не указывай по умолчанию — старт берётся с даты запуска (сегодня); задавай его, только если пользователь явно назвал дату начала.
Понимает подписанную форму (`Фича: аналитика 2 нед, разработка 3 спринта, тестирование 2 нед`, метки — слово или буква А/Р/Т) и позиционную (`Фича: 2 нед, 3 спринта, 2 нед` или через `|`/`;`, пустая ячейка = фазы нет). Поддержка `xN` (число людей, `people`) и `/ Имя` (исполнитель) в оценке. Порядок строк = приоритет. Схема результата — та же `features.json`.

### Источник: выгрузка эпиков из Jira

Частный случай режима B — CSV-экспорт эпиков из Jira. Конвертер собирает `features.json` сам:
```bash
python scripts/jira_to_features.py epics.csv features.json \
    [--capacity analytics:10,dev:15,testing:10] [--start 2026-07-20] [--title "..."] [--today ...] [--sprint-weeks 2] [--allow-gaps]
```
`--start` по умолчанию не задавай — старт берётся с даты запуска (сегодня).
Маппинг: Summary → имя фичи, Priority (Highest/High/…) → `priority`, Assignee/Team → `owner`, Components → `services`, кастом-поля оценок аналитики/разработки/тестирования → фазы (ячейки вида «3 спринта x2» → спринты + `people`), «Зависит от»/Epic Link (ключ) → `after`, «Веха» → `milestone`. Колонки ищутся по ключевым словам в заголовке (терпит вариации имён); эпики в статусе Done/Closed отбрасываются. Дальше — обычный `plan_features.py` → рендер. Проверь сводку конвертера (что распозналось, что пропущено) перед планированием.

## Режим B: список фич с оценками

Типичный вход: согласованный и приоритизированный список фич; по каждой — оценки аналитики, разработки, тестирования (по умолчанию в человеко-днях; можно в неделях или спринтах), опционально исполнители и финальная веха («Выход на КО»). Источник — слова пользователя, таблица или выгрузка из Jira (см. выше).

- **По умолчанию — фичи параллельно, без вопросов.** Получив список фич, сразу собирай `features.json` **без `capacity`** и строй roadmap с максимальной параллельностью: все фичи стартуют одновременно и идут независимо. Не спрашивай про capacity, размер команды, старт, длину спринта и т.п. — бери дефолты и строй. Уточняй что-либо, только если без этого нельзя понять сами оценки фаз.
- Оценки бери из слов пользователя как есть. По умолчанию число — это **трудозатраты в человеко-днях (чд)**; в параллельном дефолте (без `capacity`) чд-оценка фазы считается на одного человека и переводится в длительность как `чд / work_days` недель. Если команда мыслит в неделях/спринтах — задавай оценку явной формой `{weeks}`/`{sprints}`. Длина спринта (`sprint_weeks`) по умолчанию 2, рабочих дней в неделе (`work_days`) — 5; не переспрашивай эти значения.
- **Дату старта в Режиме B не спрашивай.** По умолчанию roadmap строится от даты запуска (сегодня) — не задавай `start` и не задавай `--start` конвертерам, планировщик сам возьмёт текущую неделю. Задавай `start` только если пользователь сам явно назвал дату начала; никакого уточняющего вопроса про старт/период задавать не нужно.
- `capacity` — **опциональный** рычаг, включай его, **только если пользователь сам сказал**, что команда одна и делит общий ресурс (например: «у нас одна команда», «capacity 15 чд/спринт», «фичи в один поток»). Это пропускная способность команды в чд за период: сколько работы команда реально выдаёт с учётом отвлечений (например, 3 разработчика дают 15 чд за спринт → `"dev": 15` при `capacity_per: "sprint"`). Число — общий пул, объект `{analytics, dev, testing}` — пулы по стадиям. Период задаёт `capacity_per`: `"week"` — чд/нед (по умолчанию), `"sprint"` — чд/спринт (в импортёрах — флаг `--capacity-per sprint`). Чд-оценка фазы без явных `people` потребляет весь пул фазы: длительность = чд / пул (30 чд разработки при 15 чд/спринт = 2 спринта), такие фичи идут в фазе по очереди, конвейером. Без `capacity` (дефолт) чд-оценка считается на 1 человека, фичи параллельны — это и есть основной режим.
- Фазы фичи идут в порядке аналитика → разработка → тестирование **с нахлёстом по умолчанию** (`overlap: 0.5` — следующая фаза стартует, когда предыдущая наполовину готова; типовая практика: разработка начинается по первым готовым требованиям). Разрывы внутри фичи запрещены: если пул какой-то фазы занят, сдвигается вся фича целиком. Фичи занимают ресурсы в порядке списка, не влезающие — сдвигаются (планировщик печатает сдвиги). Нахлёст настраивается полем `overlap` (доля предыдущей фазы или целые недели, глобально или на фичу); **строгая последовательность фаз — `"overlap": 0`**, задавай её, если пользователь говорит, что фаза не может начаться до полного конца предыдущей (исследовательская фича, жёсткий контракт). Разрывы между фазами можно разрешить `"allow_gaps": true`. Жёсткую последовательность фич задавай `after` (или явным `start`).
- Раскладка по людям опциональна: `who` в оценке фазы попадает в подпись полосы, `owner` фичи — в левую колонку, `people` — сколько человек занято в фазе (тогда её темп = `people × work_days` чд/нед вместо всего пула; для оценок длительностью — трудозатраты в подписи = `people × длительность × work_days` чд). Без них roadmap строится так же.

## Редактирование существующего roadmap

Готовые .pptx/.xlsx **никогда не правь напрямую** — они целиком генерируются из
JSON, и любая ручная правка фигур затрётся при следующей генерации. «Режим
редактирования» — это правка JSON + перезапуск рендереров (секунды):

```bash
python scripts/build_xlsx.py roadmap.json roadmap.xlsx
python scripts/build_pptx.py roadmap.json roadmap.pptx
```

На каком уровне править — зависит от типа изменения:

- **Изменились оценки, приоритеты, состав фич** (фича стала длиннее/короче,
  добавилась/выпала, поменялся порядок) → правь `features.json` и прогони
  планировщик заново (`plan_features.py`): он сам пересчитает каскадные сдвиги
  остальных фич с учётом `capacity`.
- **Точечный ручной сдвиг** («передвинь эту полосу на 2 недели», «веха переехала
  на 15.09», поправить подпись/выноску) без пересчёта остальных → правь готовый
  `roadmap.json` (даты `start`/`end` полосы, `date` вехи) и сразу рендери.
- **Roadmap из режима A** (исходник — Excel-план): слоя `features.json` нет,
  все правки — прямо в `roadmap.json`.

Осторожно: ручные правки в `roadmap.json` живут до первого перезапуска
планировщика — `plan_features.py` перезаписывает файл целиком. Если ручных
правок много и они важны, либо перенеси их причину в `features.json`
(явный `start`, `after`, изменённая оценка), либо больше не запускай
планировщик для этого roadmap. Типичный запрос пользователя формулируется
словами («сдвинь тестирование фичи X на неделю») — переведи его в правку
нужного уровня сам, не заставляй пользователя редактировать JSON.

После любой правки перегенерируй **оба** файла (xlsx и pptx), чтобы они не
разошлись, и проверь их программно, как описано в «Ограничения и типичные
ошибки».

## Как разбирать исходный план

Типичный исходник: шапка из 2–3 строк (месяц / «Спринт N» / диапазон дат недели «20.07-26.07»), в первой колонке (или нескольких) — человек/команда/направление, в ячейках — тексты задач, иногда с тегами вида `[SDD]`, `[Сделки_ДЗО]`.

Правила интерпретации:
- **Колонка недели** задаёт даты: неделя с понедельника. Диапазоны вида «29.06 - 05.07» парси по первой дате; год бери из контекста листа (шапки месяца) или спроси.
- **Одна и та же задача в соседних ячейках подряд** = одна полоса (bar) от первой до последней недели. Сравнивай тексты нечётко: одинаковый префикс/тикет — та же задача.
- **Цвет заливки несёт смысл** (уточни у пользователя при первом использовании и запомни): в типичном исходнике жёлтый = отпуск или «Выход на КО», зелёный = завершено/особый статус, красный текст = риск/блокер.
- **Отпуск** — рендери как полосу style `vacation`.
- **Дорожки roadmap — это фичи, а не люди.** Каждая `group` — фича/эпик/направление («Интеграция с IDP», «Требования к агентам»), конкретные подзадачи — `rows` внутри группы. Фичу определяй по тегам (`[SDD]`, `[Сделки_ДЗО]`), тикетам и общему префиксу текста задач. Если в исходнике строки — люди, перегруппируй: собери задачи одной фичи от разных людей в одну дорожку, а человека укажи в `owner` группы (или упомяни в `label` строки, если внутри фичи владельцы разные). Одна фича у нескольких людей = одна группа. Не плоди пустые дорожки: у фичи с одной задачей — одна строка.
- **Дорабатываемые сервисы фичи** — в `services` группы. По каждой фиче перечисли предполагаемые сервисы/системы, которые придётся дорабатывать: бери их из тегов, текста задач и названий интеграций (CTL, ClickHouse, IDP, СберЧат и т.п.). Список показывается в левой колонке под владельцем («Сервисы: …»). Если из исходника сервисы не видны — включи вопрос про них в единый уточняющий вопрос пользователю, а не выдумывай; при отсутствии ответа поле опусти.
- **Персональные события** (отпуск, «Выход на КО») не размазывай по фичам: вынеси их в отдельную группу «Команда» в конце roadmap. Исключение — отпуск, который прямо объясняет разрыв в полосе конкретной фичи: его можно оставить строкой внутри этой фичи.
- Однонедельные события с глаголом завершённости («Подготовлен драфт», «Выход на КО») — это **вехи** (milestone), а не полосы.
- **Несколько вех одной задачи — в одну строку.** Если у задачи несколько контрольных точек («Выход на КО» в трёх датах), клади их как несколько milestone-элементов в `items` одной строки, а не тремя одинаковыми строками — иначе roadmap раздувается пустыми дорожками. Пара «полоса + завершающая веха» одной задачи — тоже одна строка.
- **Подписи полос — короткие.** Внутри полосы помещается примерно 2 символа на неделю ширины; для короткой полосы оставь тикет/ключевые слова (`ARGUSRA-5698`, «Лимиты ОФР»), полный текст задачи уже есть в подписи строки (`label`), а детали можно унести в `note`. Рендерер сам ужмёт и усечёт слишком длинный текст с «…», но лучше до этого не доводить.

Если структура исходника непонятна (нестандартная шапка, несколько листов) — задай пользователю один компактный вопрос со своей лучшей гипотезой, не бомбардируй вопросами.

## Что уточнить у пользователя

**Режим B — по умолчанию не спрашивай ничего.** Строй roadmap сразу на
дефолтах: старт = сегодня, `sprint_weeks` = 2, `work_days` = 5, фичи
максимально параллельны (без `capacity`), фазы с нахлёстом (`overlap` 0.5 по
умолчанию). Никаких вопросов про старт, период, длину спринта, нахлёст —
эти рычаги имеют дефолты и меняются потом одной фразой. Общий пул (`capacity`)
подключай молча, когда пользователь сам назвал цифры.

**Спрашивай только когда данных реально не хватает** — когда без ответа
нельзя честно собрать `features.json`, а гадать = наврать в сроках:

- у фичи **нет ни одной оценки фазы** — не выдумывай оценку сам;
- **оценка без единиц** и из контекста непонятно («разработка — 5»: чд?
  недели? спринты?);
- пользователь **упомянул команду/капасити, но не дал цифр** («у нас одна
  команда», «есть ещё QA») — спроси чд за спринт по фазам, не подставляй
  типовые числа молча.

Все накопившиеся уточнения собери в **один компактный вопрос** (лучше с твоей
гипотезой по умолчанию), а не серию. Чего в вопросе быть не должно: старт,
длина спринта, нахлёст, «а сколько у вас людей» при уже названном капасити.

**Режим A** (Excel-план): если не сказано явно — уровень детализации (все задачи
или только ключевые вехи/полосы), дата «сегодня»-линии, дорабатываемые сервисы по
фичам (если не восстанавливаются из исходника). Разумные дефолты: все задачи,
сегодняшняя дата, сервисы — только те, что явно видны в исходнике. Период берётся
из самого исходника.

## Стили (зашиты в рендереры)

| Элемент | Вид |
|---|---|
| milestone `done` | зелёный ромб ◆ |
| milestone `planned` | белый ромб с красным контуром |
| bar `work` | оранжевая полоса, подпись внутри |
| bar `estimate` | бледно-жёлтая полоса (оценки «N спринтов, K чд») |
| bar `analytics` | голубая полоса (аналитика/SDD) |
| bar `testing` | сиреневая полоса (тестирование) |
| bar `vacation` | жёлтая полоса «Отпуск» |
| note | голубая выноска с текстом |
| today | зелёная вертикальная линия/подсветка недели |
| флажок старта roadmap | синий вымпел «Старт» + вертикальный шест на левой границе первой недели |
| флажок конца roadmap | красный вымпел «Финиш» + вертикальный шест на правой границе последней недели |
| маркер старта фичи | синий ромбик (как в легенде) на левом крае первой полосы фичи |
| маркер финиша фичи | красный ромбик на правом крае последней полосы фичи |

Флажки границ roadmap **и ромбики старта/финиша каждой фичи** рисуются **по
умолчанию в обоих режимах** (A и B) и в обоих форматах (xlsx и pptx) — рендерер
сам ставит их по `start`/`end` roadmap и по крайним полосам каждой фичи (в pptx —
ромбик, в xlsx — цветная граница столбца по строкам фичи).
Выключить границы roadmap — `"flags": false`, маркеры фич — `"feature_flags": false`;
переопределить подписи границ — `start_label` / `end_label`.

## Ограничения и типичные ошибки

- В pptx на один слайд помещается 15 строк дорожек — рендерер сам паджинирует, шапка повторяется. Не пытайся ужать всё в один слайд, уменьшая шрифт ниже 8pt.
- Русские подписи длинные: в xlsx подпись полосы кладётся в объединённый диапазон полосы; если текст длиннее полосы — сократи подпись в JSON (например, до тикета), полный текст унеси в `note`.
- Даты в JSON только ISO (`YYYY-MM-DD`). Все преобразования дат делай на этапе парсинга.
- **Диапазон roadmap должен покрывать задачи.** Полоса, выходящая за `start`/`end`, обрезается по границе и помечается стрелкой «→»/«←»; вехи и выноски вне диапазона пропускаются с предупреждением в консоли. Если видишь такие предупреждения — либо расширь диапазон, либо подтверди у пользователя, что усечение намеренное.
- После генерации обоих файлов открой их программно (openpyxl / python-pptx) и проверь: количество дорожек совпадает с JSON, нет полос с нулевой шириной, вехи попали в диапазон дат. Потом отдай файлы пользователю.
