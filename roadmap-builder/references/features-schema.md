# Схема features.json

Вход для `plan_features.py` — согласованный список фич с оценками фаз.
Планировщик сам раскладывает фазы по неделям и генерирует `roadmap.json`
для рендереров.

```json
{
  "title": "Roadmap: Агентская платформа Q3",
  "subtitle": "приоритеты согласованы 14.07",
  "start": "2026-07-20",
  "today": "2026-07-16",
  "sprint_weeks": 2,
  "work_days": 5,
  "capacity": {"analytics": 10, "dev": 25, "testing": 10},
  "capacity_per": "sprint",
  "features": [
    {
      "name": "Интеграция с IDP",
      "priority": 1,
      "owner": "Команда А",
      "services": ["IDP", "CTL"],
      "analytics": 20,
      "dev": {"days": 60, "people": 2, "who": "Петров"},
      "testing": {"weeks": 2, "who": "Сидорова"},
      "milestone": "Выход на КО"
    },
    {
      "name": "Лимиты ОФР",
      "priority": 2,
      "after": "Интеграция с IDP",
      "analytics": {"weeks": 1, "who": "Иванов"},
      "dev": {"sprints": 2}
    }
  ]
}
```

## Корень

| Поле | Обязательное | Описание |
|---|---|---|
| `title` | да | Заголовок roadmap |
| `subtitle` | нет | Подзаголовок |
| `start` | нет | Дата старта планирования, ISO. Округляется к понедельнику. Без неё — дата запуска планировщика (сегодня) |
| `end` | нет | Правая граница roadmap. По умолчанию — конец самой поздней фичи |
| `today` | нет | Дата линии «сегодня» |
| `flags` | нет | Флажки границ («Старт» слева, «Финиш» справа). По умолчанию `true`; `false` — выключить. Пробрасывается в roadmap.json |
| `start_label` / `end_label` | нет | Подписи флажков старта/конца (по умолчанию «Старт»/«Финиш») |
| `sprint_weeks` | нет | Недель в спринте для оценок в спринтах. По умолчанию 2 |
| `work_days` | нет | Рабочих дней в неделе — переводит длительность в человеко-дни. По умолчанию 5 |
| `capacity` | нет | Пропускная способность команды в человеко-днях — сколько чд работы команда реально выдаёт за период (с учётом отвлечений): число — общий пул на все фазы; объект `{"analytics": N, "dev": N, "testing": N}` — независимые пулы (нет ключа — фаза без ограничения). Единица периода — см. `capacity_per`. Определяет и длительность чд-оценок (см. «Оценка фазы»), и очередь фич. Без `capacity` все фичи идут параллельно |
| `capacity_per` | нет | Период `capacity`: `"week"` — чд в неделю (по умолчанию); `"sprint"` — чд в спринт (делится на `sprint_weeks` → чд/нед). Пример: 3 разработчика с учётом отвлечений дают 15 чд за 2-недельный спринт → `"dev": 15`, `"capacity_per": "sprint"` = 7.5 чд/нед |
| `allow_gaps` | нет | `true` — разрешить разрывы между фазами фичи (жадный режим). По умолчанию `false`: фазы встык, фича сдвигается целиком |
| `overlap` | нет | Нахлёст фаз: следующая фаза стартует до конца предыдущей. Доля `0..1` — от длительности предыдущей фазы (`0.5` — разработка стартует после половины аналитики), целое `>= 1` — недель нахлёста. Объект по фазе-приёмнику — разные нахлёсты на переходах: `{"dev": 0.5, "testing": 0.3}` (вход в разработку / в тестирование; не названная фаза — дефолт `0.5`). Ограничен так, что следующая фаза стартует минимум через неделю после предыдущей. Задаётся в корне (на все фичи) и/или у фичи (`features[].overlap` — переопределяет). **По умолчанию `0.5`**; строгая последовательность (фазы встык) — явный `"overlap": 0`. Капасити при нахлёсте учитывается честно: недели, где фазы одной фичи делят общий пул, суммируются |
| `features` | да | Список фич — в порядке приоритета, если нет поля `priority`. При заданном `capacity` порядок = приоритет в очереди за ресурсами |

## feature

| Поле | Обязательное | Описание |
|---|---|---|
| `name` | да | Название фичи (уникальное) — имя дорожки roadmap |
| `priority` | нет | Число; если задано хотя бы у одной фичи, список сортируется по нему |
| `owner` | нет | Ответственный (человек/команда) — в левой колонке под названием |
| `services` | нет | Массив дорабатываемых сервисов/систем |
| `start` | нет | Явная дата старта фичи (иначе — глобальный `start`) |
| `after` | нет | Имя фичи-предшественника: старт со следующей недели после её конца. Предшественник должен идти в списке раньше |
| `analytics` | * | Оценка фазы «Аналитика» (голубая полоса) — чд или длительность, см. «Оценка фазы» |
| `dev` | * | Оценка фазы «Разработка» (оранжевая полоса) — чд или длительность |
| `testing` | * | Оценка фазы «Тестирование» (сиреневая полоса) — чд или длительность |
| `milestone` | нет | Строка (подпись) или `true` — планируемая веха ◇ в понедельник после последней фазы |

\* — хотя бы одна из трёх фаз обязательна. Фазы идут в порядке
аналитика → разработка → тестирование, по умолчанию с нахлёстом
(следующая стартует до конца предыдущей — см. `overlap` в «Корне»).

## Оценка фазы

По умолчанию оценка — **трудозатраты в человеко-днях (чд)**; длительность фазы
планировщик выводит сам. Формы:

- **число** — трудозатраты в чд: `"analytics": 20` (= 20 чд)
- **`{"days": N, "people": M, "who": "...", "label": "..."}`** — чд (алиасы ключа: `чд`, `effort`)
- **`{"weeks": N, "people": M, "who": "...", "label": "..."}`** — длительность в неделях
- **`{"sprints": N, "people": M, "who": "...", "label": "..."}`** — длительность в спринтах (× `sprint_weeks`)

- **Для чд-оценки** длительность выводится из пропускной способности.
  Без явных `people` фаза потребляет **весь пул своей фазы** (команда как
  целое): `недель = чд / пул(чд/нед)`, округление вверх до целых недель.
  Пример: `"dev": 30` при `capacity {"dev": 15}, capacity_per: "sprint"`
  (= 7.5 чд/нед) → 4 нед. С явными `people`: `недель = чд / (people ×
  work_days)` — `{"days": 30, "people": 3}` → 2 нед. Без пула и без `people`
  считается 1 человек: `"dev": 30` → 6 нед. Загрузка пула распределяется
  равномерно (`чд / недель`), так что суммарно фаза списывает из пула ровно
  свои чд.
- **Для оценки длительности** (`weeks`/`sprints`) трудозатраты выводятся:
  `чд = people × длительность(нед) × work_days` («3 спринта, 60 чд» при
  `sprint_weeks: 2`, `work_days: 5`, `people: 1`); `people` по умолчанию 1,
  загрузка пула = `people × work_days` чд/нед.

Подпись полосы — «N нед, M чд». `who` дописывается к ней («2 нед, 30 чд /
Петров»), `label` полностью заменяет автоподпись. Дробные длительности
допустимы — полоса округляется вверх до целых недель.

## Как `capacity` влияет на планирование

`capacity` — единственный рычаг сроков, а не «режим-тумблер». Без него ресурсы
не ограничены и фичи идут параллельно (`features_parallel.json`). С ним фичи
делят общий пул: набиваются в бак пропускной способности, что не влезло —
разливается на следующие спринты (`features.json`). Чд-оценка без `people`
занимает весь пул фазы, поэтому такие фичи идут в фазе по очереди — подробнее
ниже. Простой разбор с примерами — в `input-guide.md`.

## Планирование по капасити

Фичи обрабатываются в порядке списка и идут параллельно, пока влезают в
капасити пулов. **Фазы одной фичи не разрываются**: цепочка аналитика →
разработка → тестирование ставится встык и сдвигается целиком до первого
окна, где каждый пул свободен в свои недели, — аналитика не стартует раньше,
чем разработка сможет подхватить её без паузы. Сдвиги печатаются в сводке.

Чд-оценка без `people` занимает весь пул своей фазы — команда делает такие
фичи в этой фазе строго по очереди (конвейером: пока фича 1 в разработке,
фича 2 может идти в аналитике). Параллельность внутри фазы появляется, когда
у фаз заданы `people` меньше пула. Без `capacity` фичи параллельны без
ограничений.

`"allow_gaps": true` в корне включает старый жадный режим: каждая фаза
стартует в первый свободный понедельник по отдельности — фича может
разорваться (аналитика сделана, разработка ждёт пул).

## Ограничения

- Явные `after`/`start` — нижняя граница старта фичи, капасити может сдвинуть
  её позже, но не раньше.
- Нахлёст фаз внутри фичи задаётся полем `overlap` (см. «Корень»): по
  умолчанию `0.5`, строгая последовательность (фазы встык) — явный
  `"overlap": 0`.
