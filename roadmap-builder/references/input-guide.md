# Входные данные: с чего начать (просто)

Чтобы получить roadmap, скиллу нужен **один** из двух видов входа. Выбери свой
и дай минимум — остальное скилл достроит и спросит только если непонятно.

## Вид входа 1 — готовый Excel-план работ (Режим A)

У тебя уже есть таблица: спринты/недели в колонках, люди или команды в строках,
задачи в ячейках. Просто пришли этот `.xlsx` — скилл разберёт его сам
(цвет заливки ячеек тоже читается: жёлтый — отпуск, зелёный — done и т.п.).
Ничего заполнять руками не нужно. Детали разбора — в `data-schema.md`.

## Вид входа 2 — список фич с оценками (Режим B)

У тебя есть согласованный список фич, и по каждой — оценки трёх фаз:
**аналитика → разработка → тестирование**. Это самый простой вход. Дать можно:

- **текстом** — одна строка на фичу (`scripts/text_to_features.py`);
- **выгрузкой эпиков из Jira** — CSV (`scripts/jira_to_features.py`);
- **готовым `features.json`** — см. пример ниже и полную схему в `features-schema.md`.

Скилл сам разложит фазы по неделям планировщиком `plan_features.py`.

**По умолчанию фичи идут параллельно** — все стартуют сразу и не делят ресурсы.
Ничего для этого задавать не нужно; вопросов по дефолтным параметрам (старт,
спринт, нахлёст, капасити) скилл не задаёт — дал список фич, получил
параллельный roadmap. Спросит он только если в самих данных дыра: фича без
единой оценки, оценка без единиц, капасити упомянут без цифр. Эталон вывода —
`roadmap_parallel.xlsx` / `roadmap_parallel.pptx` из `features_parallel.json`.

**Фазы внутри фичи тоже идут с нахлёстом по умолчанию** (`overlap: 0.5`):
разработка стартует, когда аналитика наполовину готова, тестирование — с
середины разработки. Строгая последовательность фаз — явный `"overlap": 0`;
свой нахлёст — доля (`0.33`) или недели (`1`), можно отдельной фиче.

### Оценки: по умолчанию — человеко-дни (чд)

Число у фазы — это **трудозатраты в чд**, а не длительность. Сколько это займёт
недель, планировщик считает сам. Если команда мыслит в неделях/спринтах —
пиши явно: `{"weeks": 2}` или `{"sprints": 3}`.

## Как `capacity` влияет на сроки

Всё планирование — один расчёт: «поставь каждую фичу настолько рано, насколько
позволяют её ресурсы». Единственный рычаг — поле `capacity` (пропускная
способность команды). Это не «режим-тумблер», а размер бака ресурсов. **По
умолчанию `capacity` нет** — и это основной, ожидаемый режим (фичи параллельно).

### Без `capacity` — ресурсы не ограничены (дефолт)

Это режим по умолчанию. У каждой фичи как будто свои выделенные люди: фичи
стартуют одновременно и идут независимо. Чд-оценка без `people` считается на
одного человека. Подходит почти всегда; отдельно включать ничего не нужно.

```json
{
  "title": "Roadmap: подключение агентов (фичи параллельно)",
  "today": "2026-07-16",
  "sprint_weeks": 2,
  "work_days": 5,
  "features": [
    {"name": "Подключение агента хронологии", "priority": 1, "analytics": 20, "dev": 30, "testing": 40},
    {"name": "Подключение ESG",              "priority": 2, "analytics": 10, "dev": 10, "testing": 30}
  ]
}
```

Готовый пример в корне проекта: `features_parallel.json`.

### С `capacity` — общий пул (бак пропускной способности) — только по явной просьбе

Включай, только если пользователь сам сказал, что команда одна и делит общий
ресурс. Команда — общий бак: каждую неделю в него набивается работа разных фич, пока в
сумме влезает; что не влезло — разливается на следующие спринты. `capacity_per`
задаёт единицу: `"sprint"` — чд за спринт, `"week"` — чд за неделю.

**Важно про обычный вход — чд без `people`:** такая фаза занимает **весь пул**
целиком, поэтому в одной фазе фичи идут **по очереди** (пайплайн по фазам: пока
фича 1 в разработке, фича 2 уже в аналитике). Чтобы несколько фич делили один
пул параллельно, задай `people` в фазах — тогда каждая берёт только
`people × work_days` чд/нед.

```json
{
  "title": "Roadmap: подключение агентов (одна команда, конвейер)",
  "today": "2026-07-16",
  "sprint_weeks": 2,
  "work_days": 5,
  "capacity": {"analytics": 10, "dev": 20, "testing": 15},
  "capacity_per": "sprint",
  "features": [
    {"name": "Подключение агента хронологии", "priority": 1, "analytics": 20, "dev": 30, "testing": 40},
    {"name": "Подключение ESG",              "priority": 2, "analytics": 10, "dev": 10, "testing": 30}
  ]
}
```

Готовый пример в корне проекта: `features.json`.

### Что задать

| Ситуация | Что задать |
|---|---|
| **По умолчанию** — фичи параллельны, ресурсы не общие | ничего: `capacity` не задавать |
| Пользователь явно сказал: одна команда с конечной пропускной способностью | задать `capacity` + `capacity_per` |

Оба конвертера (`text_to_features.py`, `jira_to_features.py`) задают `capacity`
флагом `--capacity analytics:2,dev:3,testing:2` (и `--capacity-per sprint`). Без
него ресурсы не ограничены.

## Минимальный набор полей (Режим B)

| Поле | Обязательное | Зачем |
|---|---|---|
| `title` | да | Заголовок roadmap |
| `features[].name` | да | Название фичи = дорожка roadmap |
| `features[].analytics` / `dev` / `testing` | хотя бы одна | Оценки фаз в чд |
| `today` | нет | Линия «сегодня» |
| `start` | нет | Дата старта (по умолчанию — сегодня) |
| `capacity` + `capacity_per` | нет | Общий пул ресурсов. Чд без `people` → в фазе по очереди |
| `priority` | нет | Порядок в очереди за пул (важно, когда задан `capacity`) |
| `owner`, `services`, `who`, `people`, `after`, `milestone` | нет | Детализация — см. `features-schema.md` |

Всё остальное (длина спринта, рабочие дни, флажки границ, вехи, зависимости)
имеет разумные значения по умолчанию. Полная схема — в `features-schema.md`.

## Roadmap уже построен, нужно поменять

Готовые .pptx/.xlsx руками не редактируются — просто скажи, что изменить
(«сдвинь тестирование фичи X на неделю», «веха переехала на 15.09», «оценка
разработки теперь 40 чд»). Правка вносится в JSON, файлы перегенерируются за
секунды. Куда именно вносится правка (в `features.json` с пересчётом плана или
точечно в `roadmap.json`) — решает скилл, см. раздел «Редактирование
существующего roadmap» в SKILL.md.
